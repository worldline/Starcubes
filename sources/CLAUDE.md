# `sources` — file notes

File-by-file notes for `sources`, split out of the root `CLAUDE.md` so they
load only when work touches this directory. The project-wide rules — git
workflow, code conventions and the verification checklist — stay in the
root [`CLAUDE.md`](../CLAUDE.md); read that one too.

| File | Purpose |
|------|---------|
| `sources/accounts.py` | The auth_user contact/preference columns the Django model does not know (`xmpp_jid` 0030; `notify_email`/`notify_xmpp` 0032, deliberate default off) — one module owns the raw SQL so the column list cannot drift between callers. Django-free, engine-first (functions take the engine; `_meta_engine()` stays in views.py). `CONTACT_COLS` is the canonical column list `recipients_list` and `alarm_notify._resolve_lookups` build their SELECTs from. |
| `sources/views.py` | Datasource CRUD + ETL JSON endpoints. Three role-gating decorators near the top — `@_login_required_json`, `@_admin_required_json`, `@_admin_required_page` — wrap every endpoint that needs one (the user-facing *pages* rely on `RequireLoginMiddleware` instead); the list / detail / me pages are open to logged-in users, everything configuration-shaped is superuser-only. `source_detail` and `source_manage` are two thin entries into one `_render_source_page`: both render `source.html`, the first at the remembered detail level, the second forced to Expert and gated `@_admin_required_page`. What a non-superuser may see is decided inside, by `expert_allowed`. `source.html` reads `?apply=<slug>` / `?save-profile=1` for deep-links from the profile catalogue, and `?tab=` for the chart's. Group dimensions live under `group-dims/`. Alarms under `alarms/` — login-only CRUD with `context_filter` jsonb + `alarm_history` snapshot on every write, plus read-only `history/`/`firings/`/`match-context/` endpoints and the server-rendered episode overview — global at `/sources/alarms/firings/` (`alarm_firings_page`), per-datasource as the page's Firings tab, both off `_firing_episodes` + `firings_context` + `sources/_firings.html` so the two cannot drift (`scoped` swaps the datasource dropdown for an "All firings" link and drops the Datasource column); `_validate_alarm_context` reuses `core.query`'s filter validation and `check_no_grouped_filters`, `_parse_context_field` is the shared `context` parser (CRUD + match-context, so the accepted shape and its wording cannot drift), `_context_labels` wraps `resolve_context_labels` and degrades to raw ids on any failure. `_validate_alarm_notify` enforces the channel/recipient pairing at save time (one pass, absent-keeps-stored semantics; `alarm_add` normalizes absent recipient fields to `[]` BEFORE the call so a selected channel without recipients is refused, while `alarm_edit` re-checks against the effective submitted-or-stored value after loading the old row); the recipient arrays travel as absent-keeps-stored (the inline editor sends channels only). `recipients_list` (`/sources/recipients/`) is the address book the alarm forms select from — every login user with email/xmpp_jid plus the two 0032 opt-in flags (so a form can label "(not opted in)" recipients the dispatcher will drop); `settings_page` maintains `auth_user.xmpp_jid` via raw SQL (the Django model does not know the column) and scrubs a deleted user's id from the recipient arrays by hand (`int[]` cannot carry an FK). `source_edit` writes `datasource.pagerduty_routing_key` (NULLIF, empty = off). `profiles_page` renders `/sources/profiles/`; `profiles_list` is its JSON twin. `transports_page` (`/sources/transports/`, global tab) edits the global transport/SSO config — env-first resolution via `core.config`, DB rows in `starcubes_meta.app_config` (`_upsert_config`/`_unset_config`, 0031); env-set keys render disabled and are refused on write; secrets keep submitted-field semantics (absent = keep, empty = clear) and are never pre-filled; SSO applies on restart. `transports_test` sends the synthetic PagerDuty trigger+resolve (`alarm_notify.send_pagerduty_test`, dedup `starcubes-test-<ds_id>`). `my_profile` shows and self-serves the account's own `xmpp_jid` (`action=update_jid` → `_set_xmpp_jid`) and the 0032 alarm-channel opt-in (`action=update_notify` → `accounts.set_notify_optin`, deliberate default off — dispatch requires the flag). Alarm severity: per-alarm `alarm.severity` (0032) travels the same absent-keeps/empty-clears submitted-field semantics; `alarms_list` adds `has_open_episode` (EXISTS over the open `alarm_firing`) for the Alarms tab's "open" badge. `_ALARM_CHANNELS` is email/xmpp/pagerduty — `log` is not selectable any more and is silently dropped from submitted lists (legacy rows may still store it). Three historical-mutation endpoints still call `bump_cache_epoch` themselves (`etl_set_highwatermark`, `etl_clear_history`, `profile_apply`); the four delete paths moved theirs into `core/etl.py` so the CLI gets it too. Alarm endpoints deliberately do not bump — alarms feed no cache key. `etl_housekeeping` (`etl/housekeeping/`) runs `core.housekeeping.run_housekeeping` — not a dry run and not lock-guarded, so it works during forever mode; The alarm CRUD carries both `rule_kind`s: `_parse_alarm_fields(rule_kind=)` takes the **stored** kind on an edit (the inline editor never sends the field, and letting it default would rewrite a pipeline row's `measure`/`window_s` on every save), `_validate_alarm_context` returns early for a pipeline rule — which also takes `Source.load` off its save path, so a rule watching an ETL stays editable when the source DB is down — and `_episode_rule` is the one branch the Firings view needed. `insert_default_pipeline_alarms` (in `profile_store.py`) gives a new datasource two rules, enabled and channel-less, from both the GUI create form and the CLI seed. `source_edit` writes `datasource.housekeeping_interval_s`, `max_data_lag_s`, `max_run_s`, `retention_periods`, `initial_window_s` and `dim_refresh_interval_s` (all `max(0, int(...))`); `import_dims` resets `dim_refreshed_at` because it is a forced import that bypasses the interval. The ETL History query carries `extract(epoch from (src_now - max_wm)) AS data_lag_s` so the table can show the source's data lag per run without the template doing arithmetic. `etl_preflight` (`etl/preflight/`) runs `core.preflight.run_preflight` with `repair=False` — a dry run, so the button never performs DDL; the load path is what repairs, and records it on the run row. It builds the source engine defensively (a missing driver just skips the projection probe). The four destructive maintenance views no longer call `bump_cache_epoch` themselves — `core/etl.py` does it, so the CLI gets it too — and they now pass `meta_engine=`, which is what lets them rewind the watermark or raise the retention floor. `etl_kill` sends SIGTERM/SIGKILL and cleans up a dead-PID or force-killed `etl_run` row (a live-SIGTERM'd parent writes its own row via `EtlAborted`). `etl_logs`/`etl_log_tail` serve the per-run log files under `etl/logs/`/`etl/log/`. See [`docs/sources-app.md`](../docs/sources-app.md). |
| `sources/alarm_notify.py` | The alarm notification dispatcher — the Django-side counterpart to `core/alarm.py`'s transitions. `dispatch_transitions` is the only entry point the management commands call; never raises; resolves user ids/addresses and routing keys in two batched lookups and sends per channel in its own try/except (one broken SMTP server must not suppress a PagerDuty trigger). `_addresses` enforces the 0032 channel opt-in — an email/xmpp recipient without `auth_user.notify_email`/`notify_xmpp` is dropped with a WARNING (PagerDuty has no user preference); the log channel is gone from the dispatcher (the episode row + evaluator log line are always on, written by `core/alarm.py`); the PagerDuty severity is the transition's per-alarm `severity` with the global `STARCUBES_PAGERDUTY_SEVERITY` as fallback (the test event always sends the global value). `render_message` is the shared subject/body formatter; PagerDuty dedup key is `starcubes-alarm-<alarm_id>#<episode_id>` (per episode — a re-opened episode gets a fresh incident). XMPP via slixmpp, bounded by `asyncio.wait_for`; a transport that is not configured (unset env vars) is skipped with a WARNING and counted as an error, it never fails the ETL. See [`docs/alarm.md`](../docs/alarm.md). |
| `sources/templates/sources/transports.html` | The global notification-config page (global tab "Transports", superuser-only, pattern `profiles.html`). One editable form card per section (`smtp`/`xmpp`/`pagerduty`/`sso` from `views._TRANSPORT_SECTIONS` — env-set keys disabled, secrets never pre-filled, resolved value shown in the hint) plus the per-datasource routing-key table (masked via `views._mask_secret`, Edit link to the source edit page, `Send test` button → `transports_test`, small inline fetch script) and static `log`/`slack` channel rows. |
| `sources/templates/sources/source.html` | **The** datasource page, at one of two detail levels. Eleven tabs: Basics, Fact Columns, Dimensions, Dim Data, Group Dims, Measures, Indices, Storage, ETL, Alarms, Firings — Basic keeps the five that are not `.expert-only` (Basics, Group Dims, Measures, Alarms, Firings). It replaced the old `detail.html` (lean, login-only) + `manage.html` (admin-only) pair, which were meant as two detail levels but had drifted: Alarms/Firings existed only on one, six config tabs only on the other, and the only way across was a ⚙ button with no way back. **Two mechanisms, do not confuse them.** `{% if expert_allowed %}` decides whether markup is *rendered* — a non-superuser never receives the admin panels, the delete form, its csrf token, the expert `<dl>` rows or the ETL controls; that is the security boundary, since every endpoint behind them is `@_admin_required_json`. `.expert-only` + `html[data-mode]` only decides whether *rendered* markup shows, and exists for superusers alone. The switch is `_mode_toggle.html` (right end of the sub-tab bar, superuser-only); it writes `localStorage['starcubes-source-mode']`, and base.html's `{% block prepaint %}` applies the mode before first paint so expert tabs never flash. Switching down to Basic while an expert tab is open falls back to Basics. `/sources/<pk>/manage/` still exists and forces Expert, which is what keeps the profile hand-off, the post-create/edit redirects and the edit form's Cancel landing where they did. **ETL is itself sub-tabbed** — Run (Run once / Run Forever / Preflight), Maintenance (Housekeeping / Data Cleanup / Metadata / Query Cache), Schema, Audit, History, Log — using the same in-content sub-tab row as Dim Data, whose CSS in `base.html` both rows share. Those sub-panels are `.etl-subpanel`, never `.tab-panel`, because the top-level switcher clears every `.tab-panel` in the document; they stay in the DOM and only toggle `display`, because every card handler binds by id on page load. For the same reason the page has an `on(id, ev, fn)` helper: with the admin panels absent, every binding must tolerate a missing element (`cmdButton`/`wireAddForm` already did). `connection-status/` and `etl/forever/status/` are admin-gated and so are their page-load probes; `etl/status/`, which feeds the status strip, is login-gated and runs for everyone. Panels come from the partials `_group_dims_panel.html`, `_measures_panel.html`, `_alarms_panel.html`, `_firings.html`; behaviour from `_alarms_js.html` (a template, not a static .js — it resolves `{% url %}` tags) plus `group_dims.js` / `inline_edit.js`. Script tags sit in `{% block extra_js %}` after `{{ block.super }}`; the group-dimension list loads lazily on first tab click. `startEdit` is wrapped further down to re-sync the dimension source fields — that still works because `inline_edit.js` leaves it a global function declaration. |
| `sources/templates/sources/_alarms_panel.html`<br>`sources/templates/sources/_alarms_js.html` | The Alarms tab, split out of the old `detail.html` when the two pages merged: markup in the panel partial, behaviour in the JS partial. The JS half stays a **template** rather than a static `.js` because it resolves `{% url %}` tags and loops over `dimensions` / `measure_aggs` / `pipeline_conditions` at render time; it was moved verbatim, behaviour unchanged. It must be included after the panel and after `esc()` / `postJSON()` / `getJSON()` / `csrfToken()` exist — hence the split, since the markup belongs in the content block and the script in `{% block extra_js %}`. Login-only CRUD, so it renders in both detail levels. Context is shown read-only as a summary, resolved to dimension names via the list's `context_labels`; expressions are carried in from the chart's bell as `?tab=alarms&new-alarm=1&context=…` or by **Clone** (⧉, `cloneAlarm`), never edited inline; the ⓘ sub-row holds the history diff + firing episodes. **No add button** — `#alarmAddPanel` is its own card *above* the list (the table stays visible) with three states: `hidden` behind `#alarmAddHint`, `collapsed` (a context arrived from the chart's Group Dims / Measures links — the card names it and offers to open; a `.has-ctx` dot marks the tab) and `open` (bell / Clone / the collapsed button). Save and Cancel return to `collapsed` keeping the context; only Clear drops it, so a context-less (whole-datasource) alarm stays a deliberate act. Each row's `↗` links back into the chart with the alarm's context (`chartUrl`, mirrors `buildHistoryParams`; `group_by` always written, `GROUPABLE_COLS` decides whether it can name a breakdown), and rows watching a carried-in context are tinted `.ctx-match` from one `match-context?any_measure=1` lookup that feeds the duplicate hint too (`refreshContextMatches`/`applyCtxHighlight`/`renderDupHint`). The forms select notification channels (checkboxes named `notify_channels` — email/xmpp/pagerduty only, no `log`; `rowFields` appends only checked values) and per-channel recipients (two multi-selects fed from `recipients_list`, cached once in `alarmUsers`, labels annotated "(not opted in)" where the account's flag is false); recipients are form-level (add form / clone via `setAlarmRecipients`), never inline-editable — the inline editor's channel checkboxes save with absent recipient fields, which the server reads as keep-stored. `alarmChannelsDisplay` names the active channels only, comma-separated (no recipient names — read mode, user decision); the inline editor's `severity` select lives in its own narrow "Sev." column (read mode: the value or muted "global"; empty = global default), which also fixed the bug where the channels' `row-edit` span carried an inline `display:flex` that defeated `.row-edit{display:none}` and kept the checkboxes visible in read mode — the same trap the merge hit again with the Basics action row, see `.card-actions` in `base.html`. A row with `has_open_episode` wears the amber "open" badge beside its name, and a 20 s poll re-runs `refresh()` while the Alarms tab is active — suspended whenever an inline edit, the ⓘ sub-row or the add panel is open, since a rebuild wipes `tbody`. |
| `sources/templates/sources/_group_dims_panel.html`<br>`sources/templates/sources/_measures_panel.html` | Two of `source.html`'s tab panels. Neither takes parameters any more: `_measures_panel.html` used to carry a `measures_help_short` switch for the old `detail.html`'s shorter help line, and with one page there is one help line. A caller needing a permission gate wraps the include. |
| `sources/static/sources/nav.css`<br>`sources/static/sources/nav.js`<br>`sources/static/sources/datetimepicker.css`<br>`sources/static/sources/datetimepicker.js` | Shared with the **chart app**, which loads them via `{% static 'sources/…' %}` rather than keeping its own copies. `nav.js` exports `makePopover` and `closeTopPopover`; `datetimepicker.js` is the union of what the two apps had grown apart into (the chart's `trigger` option and viewport clamping, the shell's `getUTCISO()` — the latter is what keeps source.html's ETL windows from being off by the UTC offset). Field chrome stays per page: `.dtp-label` here, `.dtp-field` in the chart. **The colour palettes stay separate on purpose** — the two apps disagree on `--muted`/`--accent`/`--bg2`, and the shared CSS resolves `var(--…)` against whichever page loads it. |
| `sources/static/sources/group_dims.js`<br>`sources/static/sources/inline_edit.js` | The Group Dimensions editor (~660 lines) and the inline row editors, the latter carrying `ROW_SPECS` — each table's display columns described once and read both by `saveRow` and by source.html's row builders, which replaced the bare `row-display')[N]` indices. (`startEdit`/`cancelEdit`/`saveRow`/`deleteRow`). `group_dims.js` needs `DS_PK` and `csrfToken()` and wires itself to the panel ids **at top level**, so it must load after the markup and never deferred; it defines `GROUP_PALETTE` itself and calls nothing on load. `inline_edit.js` needs `csrfToken()`, `postJSON()` and the page's `esc()` — the latter only inside `saveRow`, which runs on click, so `esc()` must stay the null-safe variant. |
| `sources/management/commands/pipeline_watch.py` | `manage.py pipeline_watch [--interval N] [--once]` — evaluates pipeline alarms from outside the ETL process and dispatches their transitions. Started by `docker/entrypoint.sh` with `&`, with the honest caveat written there: nothing supervises it. `_cycle` never raises — a supervisor that dies on a transient DB error is worse than none, because it looks like one. |
| `sources/management/commands/etl_housekeeping.py` | `manage.py etl_housekeeping --name x [--no-analyze] [--if-due]` — the hand-run entry point for `core/housekeeping.py`. `--if-due` is what a cron-like caller would use; the forever loop calls `housekeeping_due` itself rather than shelling out. |
| `sources/management/commands/check_migration_mirror.py` | Verifies the CLAUDE.md mirror contract: every per-step `migrations/0*.sql` above the consolidated file's "Combines all previous migrations (0001–NNNN)" baseline has its `-- 00NN_*.sql` marker block in `starcubes_meta.sql`; files at or below the baseline only get a note (no markers were written when the consolidation was cut). `--quiet` suppresses the notes. |
| `sources/etl_spawn.py` | `spawn_etl_subprocess(cmd, env=, datasource_name=)` — returns `(Popen, log_path \| None)`. Opens a per-run log file under `STARCUBES_LOG_DIR` and points the child's stdout+stderr at it (instead of the historical `DEVNULL`); `prune_etl_logs`/`slugify_ds`/`log_dir` are its helpers. See [`docs/etl-engine.md`](../docs/etl-engine.md). |
| `sources/etl_logging.py` | `configure_etl_logging()` — the one place allowed to wire Django settings into `core/etl.py`'s `logging.getLogger`. Stderr handler always; optional PID-1-stdout mirror when `STARCUBES_ETL_LOG_STDOUT` is set (for `podman logs`); registers `faulthandler` on `SIGUSR1`. See [`docs/etl-engine.md`](../docs/etl-engine.md). |
| `sources/profile_store.py` | The INSERTs that write a profile into `starcubes_meta`, shared by `seed_example` and the GUI so the two paths cannot drift: `insert_datasource`, `insert_profile_children`, `delete_profile_children`, `update_datasource_scalars`. |
