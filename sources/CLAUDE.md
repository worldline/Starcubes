# `sources` — file notes

File-by-file notes for `sources`, split out of the root `CLAUDE.md` so they
load only when work touches this directory. The project-wide rules — git
workflow, code conventions and the verification checklist — stay in the
root [`CLAUDE.md`](../CLAUDE.md); read that one too.

| File | Purpose |
|------|---------|
| `sources/views.py` | Datasource CRUD + ETL JSON endpoints. Three role-gating decorators near the top — `@_login_required_json`, `@_admin_required_json`, `@_admin_required_page` — wrap every endpoint that needs one (the user-facing *pages* rely on `RequireLoginMiddleware` instead); the list / detail / me pages are open to logged-in users, everything configuration-shaped is superuser-only. The detail page is split: `source_detail` (5 sub-tabs: Basics, Group Dims, Measures, Alarms, Firings) is open; `source_manage` (12 sub-tabs incl. ETL run / log) is admin-only and reads `?apply=<slug>` / `?save-profile=1` for deep-links from the profile catalogue. Group dimensions live under `group-dims/`. Alarms under `alarms/` — login-only CRUD with `context_filter` jsonb + `alarm_history` snapshot on every write, plus read-only `history/`/`firings/`/`match-context/` endpoints and the server-rendered episode overview — global at `/sources/alarms/firings/` (`alarm_firings_page`), per-datasource as `source_detail`'s Firings tab, both off `_firing_episodes` + `firings_context` + `sources/_firings.html` so the two cannot drift (`scoped` swaps the datasource dropdown for an "All firings" link and drops the Datasource column); `_validate_alarm_context` reuses `core.query`'s filter validation and `check_no_grouped_filters`, `_parse_context_field` is the shared `context` parser (CRUD + match-context, so the accepted shape and its wording cannot drift), `_context_labels` wraps `resolve_context_labels` and degrades to raw ids on any failure. `_validate_alarm_notify` enforces the channel/recipient pairing at save time; the recipient arrays travel as absent-keeps-stored (the inline editor sends channels only). `recipients_list` (`/sources/recipients/`) is the address book the alarm forms select from — every login user with email/xmpp_jid; `settings_page` maintains `auth_user.xmpp_jid` via raw SQL (the Django model does not know the column) and scrubs a deleted user's id from the recipient arrays by hand (`int[]` cannot carry an FK). `source_edit` writes `datasource.pagerduty_routing_key` (NULLIF, empty = off). `profiles_page` renders `/sources/profiles/`; `profiles_list` is its JSON twin. `transports_page` (`/sources/transports/`, global tab) edits the global transport/SSO config — env-first resolution via `core.config`, DB rows in `starcubes_meta.app_config` (`_upsert_config`/`_unset_config`, 0031); env-set keys render disabled and are refused on write; secrets keep submitted-field semantics (absent = keep, empty = clear) and are never pre-filled; SSO applies on restart. `transports_test` sends the synthetic PagerDuty trigger+resolve (`alarm_notify.send_pagerduty_test`, dedup `starcubes-test-<ds_id>`). `my_profile` shows and self-serves the account's own `xmpp_jid` (`action=update_jid` → `_set_xmpp_jid`). Six historical-mutation endpoints call `bump_cache_epoch` (alarm endpoints deliberately do not — alarms feed no cache key). `etl_kill` sends SIGTERM/SIGKILL and cleans up a dead-PID or force-killed `etl_run` row (a live-SIGTERM'd parent writes its own row via `EtlAborted`). `etl_logs`/`etl_log_tail` serve the per-run log files under `etl/logs/`/`etl/log/`. See [`docs/sources-app.md`](../docs/sources-app.md). |
| `sources/alarm_notify.py` | The alarm notification dispatcher — the Django-side counterpart to `core/alarm.py`'s transitions. `dispatch_transitions` is the only entry point the management commands call; never raises; resolves user ids/addresses and routing keys in two batched lookups and sends per channel in its own try/except (one broken SMTP server must not suppress a PagerDuty trigger). `render_message` is the shared subject/body formatter; PagerDuty dedup key is `starcubes-alarm-<alarm_id>#<episode_id>` (per episode — a re-opened episode gets a fresh incident). XMPP via slixmpp, bounded by `asyncio.wait_for`; a transport that is not configured (unset env vars) is skipped with a WARNING and counted as an error, it never fails the ETL. See [`docs/alarm.md`](../docs/alarm.md). |
| `sources/templates/sources/transports.html` | The global notification-config page (global tab "Transports", superuser-only, pattern `profiles.html`). One editable form card per section (`smtp`/`xmpp`/`pagerduty`/`sso` from `views._TRANSPORT_SECTIONS` — env-set keys disabled, secrets never pre-filled, resolved value shown in the hint) plus the per-datasource routing-key table (masked via `views._mask_secret`, Edit link to the source edit page, `Send test` button → `transports_test`, small inline fetch script) and static `log`/`slack` channel rows. |
| `sources/templates/sources/detail.html` | Lean 5-tab datasource view (Basics, Group Dims, Measures, Alarms, Firings) accessible to every logged-in user — and **editable** by them: Group Dims, Measures and Alarms are full CRUD, gated login-only, which is the whole reason the page exists. Its Group Dims and inline-edit JS is a verbatim copy of `manage.html`'s; keep it that way. Connection / ETL status polling, inline CRUD for the Alarms tab (context shown read-only as a summary, resolved to dimension names via the list's `context_labels`; expressions are carried in from the chart's bell as `?tab=alarms&new-alarm=1&context=…` or by **Clone** (⧉, `cloneAlarm`), never edited inline; ⓘ sub-row with history diff + firing episodes), `?tab=` sub-tab deep-link, drag-and-drop in the Group Dims tab. **No add button** — `#alarmAddPanel` is its own card *above* the list (the table stays visible) with three states: `hidden` behind `#alarmAddHint`, `collapsed` (a context arrived from the chart's Group Dims / Measures links — the card names it and offers to open; a `.has-ctx` dot marks the tab) and `open` (bell / Clone / the collapsed button). Save and Cancel return to `collapsed` keeping the context; only Clear drops it. So a context-less (whole-datasource) alarm stays a deliberate act. Each row's `↗` links back into the chart with the alarm's context (`chartUrl`, mirrors `buildHistoryParams`; `group_by` always written, `GROUPABLE_COLS` decides whether it can name a breakdown), and the rows watching a carried-in context are tinted `.ctx-match` from one `match-context?any_measure=1` lookup that feeds the duplicate hint too (`refreshContextMatches`/`applyCtxHighlight`/`renderDupHint`). The Firings tab is `sources/_firings.html` scoped to this datasource (server-rendered with the page; its All / Open only links reload onto `?tab=firings`), and the Alarms header's single `Firings →` link points at it. The Manage link in the header is superuser-only and points to `source_manage`. The alarm forms select notification channels (checkboxes named `notify_channels` — `rowFields` appends only checked values) and per-channel recipients (two multi-selects fed from `recipients_list`, cached once in `alarmUsers`, resolved to names in `alarmChannelsDisplay`); recipients are form-level (add form / clone via `setAlarmRecipients`), never inline-editable — the inline editor's channel checkboxes save with absent recipient fields, which the server reads as keep-stored. |
| `sources/templates/sources/manage.html` | Superuser-only 12-tab view: Basics, Group Dims, Measures plus Fact Columns, Dimensions, Dim Data, Indices, Storage, ETL Commands, Audit, ETL History, ETL Log. **No Alarms tab** — alarms are a user concern and live on `detail.html` only. ETL run / kill / log lives here; Save as Profile / Apply Profile fire the catalogue handoff (`?apply=<slug>` / `?save-profile=1`). The Group Dims and inline-edit JS is the original that `detail.html` copies verbatim — fix bugs here first, then re-copy. |
| `sources/etl_spawn.py` | `spawn_etl_subprocess(cmd, env=, datasource_name=)` — returns `(Popen, log_path \| None)`. Opens a per-run log file under `STARCUBES_LOG_DIR` and points the child's stdout+stderr at it (instead of the historical `DEVNULL`); `prune_etl_logs`/`slugify_ds`/`log_dir` are its helpers. See [`docs/etl-engine.md`](../docs/etl-engine.md). |
| `sources/etl_logging.py` | `configure_etl_logging()` — the one place allowed to wire Django settings into `core/etl.py`'s `logging.getLogger`. Stderr handler always; optional PID-1-stdout mirror when `STARCUBES_ETL_LOG_STDOUT` is set (for `podman logs`); registers `faulthandler` on `SIGUSR1`. See [`docs/etl-engine.md`](../docs/etl-engine.md). |
| `sources/profile_store.py` | The INSERTs that write a profile into `starcubes_meta`, shared by `seed_example` and the GUI so the two paths cannot drift: `insert_datasource`, `insert_profile_children`, `delete_profile_children`, `update_datasource_scalars`. |
