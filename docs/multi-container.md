# Running several containers

Any number of identical starcubes containers may share one metadata database
— behind a load balancer, on several hosts, under Kubernetes. Every container
serves the GUI, starts ETL runs, and sees and controls every run of every other
container. When one goes away, the others take its forever sessions over.

This page is the whole picture. The details live where the code is:
[`etl-automation.md`](etl-automation.md) (locks, leases, stop requests,
adoption), [`etl-engine.md`](etl-engine.md) (logging),
[`deployment-config.md`](deployment-config.md) (proxy, keys, processes),
[`source-profiles.md`](source-profiles.md) (saved profiles).

## What has to be true outside the application

| Requirement | Why |
|---|---|
| The same `STARCUBES_SECRET_KEY` in every container | Sessions and CSRF tokens are signed with it. A container with another key refuses to start (`bootstrap` compares a fingerprint; `--rotate-secret` changes it on purpose). |
| The same `STARCUBES_ALLOWED_HOSTS`, `STARCUBES_CSRF_TRUSTED_ORIGINS`, `STARCUBES_TRUST_PROXY_SSL`, `STARCUBES_OIDC_*` | The proxy's public origin is what the browser and Keycloak see, for all of them. |
| The proxy passes `Host` unchanged (port included) and sets `X-Forwarded-Proto` | Django derives the CSRF origin and the OIDC redirect URI from them. |
| One database role for all containers, connecting directly or through **session** pooling | Liveness is read from `pg_stat_activity`, which hides another role's details; advisory locks are session-scoped. A transaction pooler breaks both. |
| A stop timeout above `STARCUBES_DRAIN_TIMEOUT_S` (25 s) | Podman defaults to 10 s — use `--stop-timeout 35`. Kubernetes' 30 s grace is enough. |
| `/healthz` as the readiness (and liveness) probe | 200 only while the database answers and the container's `node_agent` runs. |

**Not required any more:** sticky sessions, a shared volume for logs or
profiles, staggered starts, a shared PID namespace.

## How the pieces fit

**Identity.** Each container start gets an instance id
(`STARCUBES_INSTANCE_ID`, generated by the entrypoint, inherited by every
process it starts). A PID only means something inside one container; the
instance id says which one.

**Liveness is a lease, not a PID.** Every ETL, forever and rollup process keeps
one database connection of its own for its whole life and writes its
`(pg_backend_pid, backend_start)` onto the run rows it owns
(`core/lease.py`). The process is alive exactly while that backend is in
`pg_stat_activity` — every container sees the same answer, a killed process
drops out at once, and a vanished host after the TCP keepalives, about a
minute. A process that loses its lease connection stops at the next chunk
boundary, so it never writes alongside its replacement.

**One list of runs.** The view `starcubes_meta.run` lists every run of every
kind — etl, backfill, forever, rollup, audit, housekeeping — with host,
status and an `alive` column. The five history tables stay as they are.

**Stopping from anywhere.** A signal cannot cross containers, so a stop is
written onto the run (`control`): `term` is read by the process itself at its
next check; `kill` is carried out within a moment by the `manage.py
node_agent` of the container that runs the process, after it has verified the
PID against the lease. Stop Forever works through `stop_requested`, which the
loop reads every few seconds.

**Forever sessions move.** On SIGTERM a container drains
(`manage.py node_drain`): it stops its own `node_agent`, asks its runs to end,
and a forever loop finishes its load and marks itself `released`. Another
container's agent adopts it within a second. A container killed outright has
its sessions adopted within a minute, by the dead-lease rule. A session an
operator stopped is never adopted. Two containers adopting at once serialise
on a per-datasource lock.

**Starting together.** `manage.py bootstrap` holds an advisory lock for
everything that writes to the database, so containers starting at the same
moment wait for each other instead of racing `CREATE TABLE`.

**One log.** Each process ships its output line by line into
`starcubes_meta.log_line` from a local spool file; a crashed process's rest is
shipped by its container's agent. **Menu → Logs** filters all of it — and all
runs — by datasource, kind, host, level, text, run and time.

**Saved profiles** are rows in `starcubes_meta.profile`, visible to every
container.

## Processes in each container

| Process | Role |
|---|---|
| `sh` (PID 1, `docker/entrypoint.sh`) | Receives the stop signal, runs the drain, then stops uwsgi; reaps orphans. |
| `uwsgi` + `nginx` | The GUI and the JSON endpoints. |
| `manage.py node_agent` | Forced kills, forever adoption, orphaned-log shipping, log retention. |
| `manage.py pipeline_watch` | Pipeline alarms (safe to run in every container — it takes a lock). |
| `manage.py etl_run …` | Spawned per run or forever session, in whichever container started or adopted it. |

`STARCUBES_FOREVER_ADOPT=0` keeps a container from adopting — for one that
should serve the GUI but never run ETL.

## Upgrading

Migrations are additive, so an old and a new image may run side by side
during a rolling update ([`releases.md`](releases.md), "Two versions on one
database"). Static file names carry content hashes, so a page from one image
never loads another image's script. When upgrading from a single container,
keep an existing `profiles/user` volume mounted for the first start —
`bootstrap` imports its files once — and set `STARCUBES_SECRET_KEY` explicitly
before starting a second container.

**The first upgrade to a lease-aware image needs one rule:** do not run an
older image and a newer one side by side *while forever sessions are active*.
An older image judges a forever session by its PID, finds a newer container's
session dead in its own PID namespace and starts a second loop for it. The
datasource lock keeps the data safe, but two loops take turns. Upgrade the
single old container in place, or stop the forever sessions for the rollout.
Single runs, the GUI and the charts of an older image work against the
migrated database (tested with 2.0.0-beta.1).

## Limits

- A forever session adopted from a container that lost its database
  connection mid-load may find the datasource still locked by that load for a
  moment. It waits for the next iteration instead of giving up (tested: one
  retry, no overlapping loads, no duplicate rows).
- A run blocked inside one long source query only reaches its next chunk
  boundary when the query returns; a `term` waits for that, `kill` does not.
- A forced kill needs the owning container's `node_agent`. If that agent is
  dead, `/healthz` says so and the probe restarts the container — which ends
  the stuck run with it.
- Configuration edited in the GUI reaches the other containers within 30 s.
- A container lost without a drain loses at most the last second of its
  processes' logs.
