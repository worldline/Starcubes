# `viz` — file notes

File-by-file notes for `viz`, split out of the root `CLAUDE.md` so they
load only when work touches this directory. The project-wide rules — git
workflow, code conventions and the verification checklist — stay in the
root [`CLAUDE.md`](../CLAUDE.md); read that one too.

| File | Purpose |
|------|---------|
| `viz/views.py` | Every `plot_json` response carries `cache_epoch`, hit or miss — the chart's own 50 MB in-page LRU keys on the query string alone and would otherwise keep painting data whose partitions a retention drop removed; `api_source_meta` clamps its advertised `time_range.min` to `datasource.retention_floor` for the same reason — **except where a rollup reaches further back**: retention deliberately leaves the rollups alone, so below the floor they still hold correct counts and the extent widens to `rollup_extent()`'s oldest bucket. `rollup_only_below` in the same payload marks where that starts, and the chart's `updateRollupNotice` shows a one-line note when the viewport reaches into it — counts and breakdowns work there, percentiles, drill-down and filters on non-rollup columns do not. `plot_json` picks a rollup after the cache miss via `pick_rollup`, and passes `rollup_table`/`rollup_value_expr` down; None simply means fact. Chart page, plot/drill/txn JSON endpoints, `slides` (the blueprint slide deck at `/slides`, streamed from repo-root `presentation.html`) and `deck_asset` (streams the deck's assets — its own under `presentation/`, the screenshots under `docs/img/` and the logo under `viz/static/viz/` — behind resolve-guards; the deck opens standalone from the filesystem too, same relative paths). `plot_json` consults `core.cache` for cacheable `count(*)`. The four `query_*` console endpoints gate themselves with `_login_required_json` (403 JSON, not a 302) and answer user SQL errors with HTTP 200. |
| `viz/help.py` | The `/help/` views — index, one document, and `search.json` — over `core.docs`. Kept out of `views.py`, which is 900 lines of chart and query endpoints and shares nothing with this. Public by design (`RequireLoginMiddleware` guards `/sources/` and `/admin/` only), so the login page can link to it. `_flatten_toc` deliberately stops at two levels: the corpus nests four deep in places and a sidebar mirroring that is a wall. The search reads `core.docs.doc_source`, which strips a hand-written "Table of contents" section the same way the renderer does — so the search cannot offer a hit on something the page does not show — and `_plain` strips Markdown from a snippet, without which every result reads as `- [text](#anchor)`. |
| `viz/templates/viz/help_index.html`<br>`viz/templates/viz/help_page.html`<br>`viz/static/viz/help.css` | The help section's pages. Both templates `{% extends "sources/base.html" %}` — cross-app, same practice as the shared `_nav_menu.html` — which is what gives them the nav, the theme pre-paint, the icon sprite and the About dialog for nothing. `help.css` names no colour that is not a `var()` from that shell, so the theme toggle carries it; the only literals are the two Pygments blocks at the bottom, the dark one gated on `[data-theme="dark"]`. Two Pygments defaults are overridden there and should stay overridden: its hard-coded code background (a light patch on a dark page) and its red `.err` box, which this corpus earns constantly by writing `…` into SQL examples. `.page`'s `--tabs-left` indent is dropped below 900px — prose has nothing to line up with. |
| `viz/templates/viz/about.html` | The **About starcubes** dialog — markup, styles and behaviour in one self-contained include, because the two page shells that use it (`sources/base.html` and `viz/chart.html`) share no stylesheet, only the CSS custom properties and the `[data-theme="dark"]` switch both define. To put it on a page: include it once and give the menu row that opens it `id="about-open"`. Its facts come from the `about` context processor, so no view passes anything; `about.is_prerelease` draws the **pre-release** pill next to the version. The timeseries.js row links to the project on GitHub with a hard-coded URL — it is not discoverable at runtime, since the dependency's own package.json lives under `node_modules/`, which never reaches the image. See [`docs/releases.md`](../docs/releases.md). |
| `viz/templates/viz/chart.html` | `dataCache` (50 MB LRU, keyed on the query string) is cleared by `noteCacheEpoch` whenever a response's `cache_epoch` moves — its only reset path; without it a retention drop, a backfill or a watermark rewind keeps being painted from cache for as long as the tab is open. Multi-source chart UI — see [`docs/chart-app.md`](../docs/chart-app.md) and [`docs/chart-rendering.md`](../docs/chart-rendering.md). The drill-down's Alert form (`openAlarmView`/`alarmContextRows`/`saveAlarmForm`) creates real alarms with the active filters + clicked series as context; grouped **filter** columns are blocked up front, a grouped `group_by` only drops the series. The three toolbar links into the configuration — Group Dims (`#source-groupdims-link`), Measures (`#source-measures-link`) and the bell (`#alarms-link`) — are built together in `updateSourceLinks` (refreshed from `gatherParams`) and all carry the live filter as `?context=`, plus `back=` (the chart's own query string) so the sources pages' brand link returns to this exact view; only the bell adds `new-alarm=1` and opens the add form. `alarmContextParam` decides once for all three how the context travels (URL vs. the shared `sessionStorage` key). The boot IIFE calls `applySourceState` when the URL has no `group_by`, before `initTs()` — see [`docs/chart-app.md`](../docs/chart-app.md). |
