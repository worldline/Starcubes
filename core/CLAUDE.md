# `core` — file notes

File-by-file notes for `core`, split out of the root `CLAUDE.md` so they
load only when work touches this directory. The project-wide rules — git
workflow, code conventions and the verification checklist — stay in the
root [`CLAUDE.md`](../CLAUDE.md); read that one too.

| File | Purpose |
|------|---------|
| `core/source.py` | `_bounded_source_engine(dsn, dialect, timeout_ms)` — a separate cached source pool whose statements cannot outlive the run budget; per dialect because there is no portable spelling (Postgres libpq startup option, Oracle `call_timeout` on the connect event, everything else logs that it is unbounded). Reached via `source_engine(statement_timeout_ms=)`. `Source` (incl. `retention_floor`; `dedupe_from` deliberately **not** here — a forever session loads its `Source` once, so `import_fact` reads that column fresh) / `Dimension` / `FactColumn` / `FactIndex` dataclasses + `Source.load` + `_get_cached_engine` + `request_engine()` (the chart request path's own cached pool with a libpq `connect_timeout`, same warehouse/search_path as `dest_engine` — a separate pool by cache key, so the ETL pools keep waiting for a busy warehouse; a connect timeout is not a circuit breaker, see the backlog's "Engine cache fast-fail") + `init_oracle_client` (thick mode if `libclntsh.so` is on `LD_LIBRARY_PATH`; then also a class-level `do_connect` hook that puts `(COMPRESSION=on)` into every Oracle connect descriptor; the chosen mode is logged from `SourcesConfig.ready()` via `oracle_client_mode()`, because settings.py runs it before `LOGGING` exists — see [`docs/sources-app.md`](../docs/sources-app.md)) + `watermark_fact_sql()` (fact-side watermark expression, falls back to `partition_column`) + `source_now_sql()` (the source's current time as naive **UTC**, per dialect, for the window's second upper-bound term — deliberately not the session clock). Splits `dim_fact_to_table()` (regular) from `auto_dim_fact_to_table()` (auto-dims, resolved in the parent ETL process). See [`docs/etl-engine.md`](../docs/etl-engine.md). |
| `core/schema.py` | `create_fact`, `create_indices`, `drop_indices`, `import_dimensions`, `read_dimensions`, `ensure_starcubes_meta(engine, force=)`. `validate_schema_name` + `ensure_schema` — the schema name goes unquoted into ~70 f-string SQL sites, so it is constrained to `^[a-z_][a-z0-9_]{0,62}$` rather than quoted (see [`docs/star-schema.md`](../docs/star-schema.md)); `ensure_schema` is called by `create_fact`, `create_dim_tables` and `import_dimensions` alike. Partition lifecycle: `list_fact_partitions`, `create_future_partitions` (append-only, manual), `ensure_partitions_for` (gap-filling, called every `import_fact` run), `vacuum_analyze_fact`. The first three plus `_partition_name` take a `table=`/`prefix=` argument defaulting to `"fact"`, so the rollup tables (ranged on the same periods, same name suffixes) share one partition implementation rather than duplicating it; `ensure_partitions_for` also takes `unlogged=` and `require_existing=` (a rollup table legitimately starts with no partitions, `fact` never does). See [`docs/star-schema.md`](../docs/star-schema.md). |
| `core/etl.py` | `import_fact` — the three-stage pipeline; calls `ensure_partitions_for` before starting workers. `_resume_state` returns `(last_end_time, extract_from, existing_pks)`; `_overlap_pks` loads the PK set for the late-arrival overlap. The window's upper bound is `max(max_wm − watermark_lag_s, src_now − wallclock_lag_s)`, clamped up to the HWM so it can never rewind. `backfill=True` re-loads a closed window without moving the HWM. `_load_auto_dim_maps` + `_resolve_auto_dim_chunk` for parent-process auto-dim discovery. `_RunBudget` enforces `datasource.max_run_s` (raises `EtlAborted`; checked between chunks and inside `_raise_if_failed`, so both bounded queue helpers honour it) — never for a backfill, a `--start/--end` window or the initial load (`_fact_has_rows`). `_dim_refresh_due` gates `import_dimensions` on `datasource.dim_refresh_interval_s` (U4, default 0 = every run); `_source_min_watermark` + `datasource.initial_window_s` walk a catching-up load forward in bounded steps (N17 — the cap measures from the HWM, not from `extract_from`, or the late-arrival overlap eats it). `EtlAborted` for user-initiated kills; `EtlStageFailed` (+ `_put_with_abort`/`_join_with_abort`/`_raise_if_failed`) for a dead transform/load worker. Throughput metrics: `_snapshot_stats`/`_build_stats_payload` read the shared `mp.Array` into the `stats` jsonb shape (now including live `queues`/`workers`); `_rate`/`_fmt_rate` compute/format rows-per-second; `_bound_log_size` truncates the process's own log file in place. Uses `logging.getLogger(__name__)`, never `print()`. Maintenance: `truncate_last_partition`, `truncate_partition`, `drop_partition`, `delete_fact_from`, `clear_etl_history`, `set_highwatermark`, `rewind_highwatermark`. All four delete paths take the datasource advisory lock and bump the cache epoch; `delete_fact_from` is the *repair* gesture (rewinds the HWM, arms `datasource.dedupe_from` when the watermark and partition clocks differ), the partition ones are *disposal* (raise `datasource.retention_floor`, never touch the HWM — and only when the partition removed was the oldest). *Repair* also rewinds the rollups (`delete_fact_from` → `rewind_rollup_state`; a rewind, not an invalidation — the next ETL hook rebuilds the span it just reloaded). *Disposal* deliberately does **not** touch them: their rows were computed while the raw data existed and stay correct, and at two orders of magnitude smaller than `fact` keeping them is close to free — aggregates outliving their rows is the point. The consequence is that below `retention_floor` a rollup stops being a cache and becomes the only copy, which is what `unreconstructable_span` exists for: `rollup_drop` and `rollup_build --rebuild` refuse that span without `--force`, because a rebuild reads `fact` and can only restore what `fact` still has. `run_preflight` runs at the top of `import_fact`'s `try:`, before `import_dimensions`; its report is merged into `etl_run.stats.preflight`. See [`docs/etl-engine.md`](../docs/etl-engine.md). |
| `core/preflight.py` | Pre-load checks + the datasource advisory lock. `run_preflight(source, meta_engine, dest_engine, source_engine=, repair=)` returns `{checks:[{code,level,message,detail}], repairs, blocked, ran_at}` — never raises for a *finding*; `blocking_message` turns the blocks into one sentence. Eight checks: `schema_objects` (U2, creates missing tables when `repair=True`), `meta_migrations` (N16), `indices` (U10, report only, time-aware via `STARCUBES_INDEX_WARN_ROWS`/`_HOURS`), `source_projection` (U5b — a *rejected* query blocks, an *unreachable* source only warns; they raise identically, so the connection is opened before the query runs), `watermark_tip` (U1 detection, warn only) `data_staleness` (U9/N12 — `src_now - max_wm` from the newest run against `datasource.max_data_lag_s`; a *negative* lag is reported as the watermark column not holding UTC, never as a small lag), `warehouse_drift` (U5a — reads `sync_schema`'s dry-run diff; blocks on a missing column or an unsafe type, warns on a safe widening or an orphan; the execute half stays unreachable) and `alarm_windows` (alarm windows reaching below the retention floor, which are not evaluated at all). Also `relation_exists` (shared with `etl.py`'s partition gestures) and `datasource_lock`/`acquire_datasource_lock`/`release_datasource_lock` + `DatasourceLocked` — `pg_try_advisory_lock` on a **dedicated NullPool connection**, because a session lock on a pooled one is silently lost to fork-safety, `pool_recycle` and `pre_ping`. Called from `import_fact`; the GUI runs it as a dry run (`repair=False`) via `etl/preflight/`. See [`docs/etl-automation.md`](../docs/etl-automation.md). |
| `core/housekeeping.py` | The periodic work that does not belong inside a load: `run_housekeeping(source, meta_engine, dest_engine, analyze=, trigger=)` → report dict, also INSERTed into `starcubes_meta.housekeeping_run`; `housekeeping_due(meta_engine, ds_id)` reads `datasource.housekeeping_interval_s` **fresh** (a forever session holds one `Source` for life). Retention (U3b — `datasource.retention_periods`, at most `STARCUBES_MAX_RETENTION_DROPS` partitions per run, and it does **not** take the datasource lock itself because `drop_partition` already does on its own connection; clears the plot cache as well as bumping the epoch), targeted `ANALYZE` + `brin_summarize_new_values` (U6), dim fill vs. the 32767 `smallserial` ceiling measured as `max(index)` (N13), partition sizes (N14). Two non-obvious rules, both learned from real data: ANALYZE targets are the newest partitions with `pg_relation_size > 0`, never the newest partition (`forward=1` runway) and never the calendar's current one (a stalled source leaves its rows months back); and the emptiness test must be **heap** size, because `pg_total_relation_size` counts index pages and so is non-zero on every partition once `create_indices` has run. Also the rollup repair step: `refresh_rollups` closes the gap left by a run that died before its own hook, and each rollup parent gets an `ANALYZE` — a table the planner has no statistics for is read with a nested loop where it wanted a hash, and the whole point of a rollup is that the planner picks well on it. **Takes no advisory lock on purpose** — everything in it is safe alongside a running load; retention (U3b) will be the first thing here that is not. See [`docs/etl-automation.md`](../docs/etl-automation.md). |
| `core/pipeline_alarm.py` | The second alarm kind: conditions over ETL state rather than fact rows. `CONDITIONS` maps five codes (`data_stale`, `run_failed`, `no_recent_run`, `preflight_warn`, `dim_full_pct`) to a measuring function, a **label with its unit** and a title. Each answers with a *number*, which is why `cond_op`/`threshold` and `core.alarm.episode_step` are reused rather than reimplemented; `None` means "not answerable yet" and must never close a standing episode. The label goes into the transition's `measure` key — that is what let `sources/alarm_notify.py` stay untouched. Reads `starcubes_meta` **only** (no `Source.load`, no source connection), which is what lets an evaluator outside the ETL judge a datasource whose source DB is down. `pipeline_eval_lock` — non-blocking `pg_try_advisory_lock` so the three evaluators (ETL loop, request path, `pipeline_watch`) cooperate instead of racing on `ux_alarm_firing_open`. Episodes carry the **wall clock**, not the fact clock. See [`docs/alarm.md`](../docs/alarm.md). |
| `core/query.py` | `timeseries_multibar` — multibar JSON producer. Bars ordered ascending by dim count. `split_grouped_col`/`resolve_group_set`/`slugify_group_set`/`grouped_token`/`grouped_label` own the `<col>:grouped:<slug>` token; `build_group_by_indices` resolves group names for grouped drill-down. `filter_target_columns` resolves which fact columns a filter token actually reads (grouped token → its real column, filter-group name → every member, else itself) and `filter_tree_columns` walks a whole tree — `_filter_sql` and `core.rollup.pick_rollup` both go through them, so the coverage test and the WHERE clause cannot drift apart. `build_chart_sql`/`timeseries_multibar` take `rollup_table=`/`rollup_value_expr=`, pre-resolved rather than a `RollupSpec` so this module needs no import from `core.rollup` (which imports *this* one). `build_filter_tree` (flat rows → nested tree) + `validate_filter_tree`/`check_filter_col` are the shared filter validation — chart endpoints, the alarm CRUD and the evaluator all use them, so error messages must not drift. `validate_filters` is the one entry point on top of both (tree or the CLI's flat groups), and it is called from the **four `_build_where` wrappers** — `build_chart_sql`, `build_chart_legend_sql`, `_gap_where`, `_build_bar_where` — rather than from each query function. That placement is what makes it exhaustive: `_build_where` is the only code that turns a filter into SQL, so every path through it (multibar, ladder, legend/Copy-chart-SQL, drill-down, transaction list, gap profile/neighbour/scan) is covered, and a new caller is covered the day it is written. Before that, only `timeseries_multibar` and `detect_gaps` validated; `drill_down` and `list_transactions` sent the typo to Postgres and got a `42703` back, which `viz._friendly_db_error` does not translate — an HTTP 500 for a typo in the filter box. `timeseries_multibar`/`detect_gaps` still call it themselves, now purely as a fail-fast ahead of the SQL build. `_filter_sql`'s plain-fact-column branch coerces the bound values by the column's `pg_type` (`_coerce_filter_vals`, plumbed as `fact_types=` through `_build_where`/`_gap_where`) — text columns get strings, not the `int()` that turned any filter on a dim-less text column into a 500; the LIKE branch already assumed text with its `::text` cast. `timeseries_ladder` (was `timeseries_quantiles`) produces the array-per-slot family; **`LADDER_STYLES` is a set of shapes, not of sources** — `parse_ladder_agg` picks the feeder, `quantile(col)` (percentile_cont, `fact` only, and the branch *raises* if handed a rollup) or `extent(col)` (min/avg/max, foldable, `EXTENT_STYLES` only), and `normalize_rungs` owns the validation both go through. The plot key stays `percentiles` for both while the Python parameter is `rungs`: the key is the library contract and a rename would break the client with no server-side error. `MEASURE_FUNCS` deliberately does **not** gain `extent` — that is what keeps `core/alarm.py` and `sources/alarm_fields.py` rejecting it as a threshold operand without a second whitelist. `detect_gaps` — the chart gap overlay's 6σ scan — runs at a fixed 1 s granularity (`GAP_SCAN_INTERVAL_S`) whatever tier the chart shows, because its gap edges are exact txn anchors (`left_txn_ms`/`right_txn_ms`, `max`/`min` of the scan's edge buckets); it reads `fact` always (a rollup has no txn timestamps) and caps one scan at `GAP_MAX_SCAN_S` (7 days) via `gap_scan_bounds` (retention floor / HWM clamps, mirror of `gap_profile_bounds`). `gap_reference_drill` is the gap dialog's breakdown: a gap holds no rows, so it reads dimension *shares* from the profile window over the hours-of-day the gap touches — same window, same hour grouping as `gap_day_profile`, so shares and μ rest on one body of data — and scales them by μ, returning `drill_down`'s exact shape so the client renders both through one path. `_profile_integral` walks the span hour segment by hour segment and must advance `seg` at the foot of its loop — without that it re-added the first segment 400 times, which only showed on spans crossing an hour boundary and turned seconds of quiet before the full hour into a 6σ outage. Its hour keys are UTC, so every SQL grouping feeding it goes through `_utc_ts` (`extract(hour from …)` over a `timestamptz` is session-local, not UTC). The λ̂(h) day profile is `gap_day_profile` (`table=`/`count_expr=` for the rollup form, `per_day` for the estimate dialog; denominator = window length, never `count(distinct day)` — a silent day must not lift every rate) and is handed into `detect_gaps(profile=)` pre-loaded: the rollup-vs-fact decision lives in `core.rollup.pick_profile_rollup` and reaches this module as pre-resolved strings, keeping it rollup-import-free (see [`docs/chart-app.md`](../docs/chart-app.md), "The gap overlay"). See also [`docs/chart-rendering.md`](../docs/chart-rendering.md) for ladder-plot specifics. |
| `core/alarm.py` | Alarm evaluation (Django-free). `_window_below_floor` refuses to evaluate a window reaching under `retention_floor` — a truncated window makes `count(*) <` report an outage retention itself caused, while `>` only misses breaches. `episode_step` is the episode machine on its own — open/extend/close plus the `eval_end` cursor, ignorant of *why* anything breached, which is what lets `core/pipeline_alarm.py` reuse it verbatim; `stamp_transitions` adds the alarm's identity and channels (**never** an alarm column named `kind` — the transitions already use that key for opened/closed). `run_alarm_cycle(kinds=)` selects the rule kinds; `kinds=("pipeline",)` touches nothing but `starcubes_meta`. `fact_max_time` is called **once per datasource** by `run_alarm_cycle` and handed to every `evaluate_alarm` on it (`fact_max=_UNSET` sentinel, since `None` already means "empty fact"); both fact-side queries carry `STARCUBES_ALARM_TIMEOUT_MS`. `run_alarm_cycle(meta, dsn, datasource_id=, source=)` loads the enabled alarms (optionally for one datasource, optionally reusing a `Source` the caller already holds); `evaluate_alarm` evaluates the one trailing window `[hwm − window_s, hwm)` at the fact clock (`fact_max_time`), skips itself when the HWM did not move, and stamps every `alarm_firing` episode transition with that HWM; `check_no_grouped_filters` enforces the grouped-token ban on **filter columns** at save time *and* in the evaluator (a grouped `group_by` is never stored and never blocks); `measure_value_expr` owns the `count(*)` special case. Context display/compare helpers: `resolve_context_labels` (stored ids → dimension names, one query per dim table for a whole list, display-only) and `normalize_context_rows` (canonical form behind the duplicate hint). **Driven by `etl_run` after every load — there is no forever loop.** `evaluate_alarm` also returns every open/close **transition** in `counts["transitions"]` (built in the same transaction that wrote the episode row, stamped with the alarm's identity + channel config + per-alarm PagerDuty `severity`) — the Django-side dispatcher `sources/alarm_notify.py` resolves addresses (`auth_user` is Django-managed, never read here) and sends; see [`docs/alarm.md`](../docs/alarm.md). |
| `core/alarm_io.py` | The alarm export file: `dump_alarms` (rows → YAML) and `parse_alarms_text` (YAML → entries), plus `MAX_ALARM_FILE_BYTES` and the `format: starcubes-alarms/1` header an upload is checked against — a profile is recognised by its catalogue filename, this file has none. Owns the *document* only: the field semantics stay in `sources/alarm_fields.py`, the same code a form save runs through, so there is one truth about a valid alarm rather than two. Carries configuration only — never `id`, `datasource_id`, `eval_end` or the timestamps, and never `alarm_history`/`alarm_firing`. Recipients arrive already translated to usernames (`auth_user` is Django-managed and off limits here). A pipeline row is written without `measure`/`window_s`/`context_filter`, whose defaults it never reads; `context_filter` is copied verbatim. See [`docs/alarm.md`](../docs/alarm.md). |
| `core/audit.py` | `_clamp_to_floor` raises every window's start to `source.retention_floor` (below it the fact table is empty *on purpose*, so an unclamped comparison reports 100% loss); a window entirely below the floor is refused. `audit_window` — per-bucket source-vs-fact row-count reconciliation; `audit_ids` — PK set difference naming the exact missing/surplus/duplicate rows; `audit_id_details` — targeted second pass giving each named id its own watermark-column value, the `etl_run` that should have caught it, and `last_end_time − that value` as the lower bound on the needed lag (both operands source-clock, so no skew); `_fetch_id_array` — the streaming id reader (see the memory note); `gap_span` folds the gap buckets into one backfill window. No Django imports. See [`docs/etl-audit.md`](../docs/etl-audit.md). |
| `core/rollup.py` | Pre-aggregation. `RollupSpec` (a rollup **is** a column set — the core set and each marginal are the same mechanism, a marginal is just a spec with one column), `rollup_specs`, `spec_hash`, `validate_config`, `measure_columns`/`measure_expr`, `ensure_rollup_tables`/`drop_rollup_tables`, `build_rollup_sql`/`build_window`/`refresh_rollups`, `pick_rollup`, `read_rollup_states`/`write_rollup_state`/`rewind_rollup_state`, `unreconstructable_span`/`rollup_extent`, `last_ok_hwm` (the shared one — the ETL hook, housekeeping and `rollup_build` all read the watermark through it). The bucket column is **named after `source.partition_column`**, which is what keeps the query-builder change to three substitutions: to `_build_where` and the slot expression a rollup looks like a thinner `fact`. Tables are **LOGGED** unlike `fact` — a rollup is rebuildable from `fact`, but a crash discarding a year of aggregates is an expensive rebuild, and the WAL it costs is a rounding error at rollup row counts. Two invariants carry everything: `spec_hash` makes a reconfiguration degrade to `fact` rather than return numbers from the old shape, and `built_from`/`built_through` let a backwards-working backfill be usable while it runs. Percentiles can never be served (they do not sum) and `validate_config` rejects them rather than half-working — but that is a statement about the **agg form**, not the graph style: `extent(col)` wears the same ladder shapes and *is* servable, so `measure_expr` can return an `ARRAY[…]` and `pick_rollup`'s condition 4 gates on the agg. `measure_columns` gives an extent measure all four stored columns regardless of its rung list, because the rung list lives in the measure catalog and so is outside `spec_hash` — honouring it would let a rung edit reach a column that was never created. No Django imports. `pick_profile_rollup` is the gap overlay's counterpart to `pick_rollup` and a different bargain: it wants the **first** spec in `rollup_specs` order that covers the query (core set before marginal), not the narrowest — the profile is one count over the whole stream, so every covering spec costs the same shape of scan and what matters is determinism plus the operator's configured order. Its own conditions: `3600 % interval_s == 0` (a bucket that straddles hour boundaries makes `extract(hour)` report the bucket's start hour), the stored `spec_hash` matching, `[built_from, built_through]` covering the day-aligned profile window (a sub-day profile is a rate measured at nothing) and `filter_tree_columns` coverage — the same condition `pick_rollup` uses, so the coverage test and the WHERE clause cannot drift. See [`docs/rollup.md`](../docs/rollup.md) and [`docs/chart-app.md`](../docs/chart-app.md), "The gap overlay". |
| `core/rollup_advise.py` | The measurement behind the operator's column choice. One exact pass over a real window of `fact` into a TEMP base table at bucket granularity; every reported number is then an aggregation over *that*, never over `fact` again — the same coarsening-is-cheap asymmetry the rollup itself exploits. **Deliberately does not sample**: estimating distinct combinations from a sample is the unseen-species problem and undercounts rare combinations, i.e. flatters the rollup. Re-grouping the base at 24x the bucket width is an observation at 24x the density, which gives the saturation exponent. `_project`'s cap is rows-per-bucket and **not** K: K measured over one window is a *lower* bound on the real asymptote (a longer window keeps finding new combinations), so capping with it overstates the speed-up — against a 27-day hand count it turned a factor of 14 into 48. Greedy drop order scores `log(marginal_cost) / log(2 + hits)`, not the ratio: cost is multiplicative and hits are additive, and on a plain ratio a free-but-unused column outranks one that multiplies the table fivefold. No Django imports. |
| `core/cache.py` | Server-side `plot_json` cache helpers. `make_cache_key`, `is_cacheable`, `get_cached_plot`, `put_cached_plot`, `bump_cache_epoch`, `clear_cache`. `make_cache_key(kind=)` namespaces the key space so unrelated payloads cannot collide (`kind="gap_profile"` — the gap overlay's day profile, whose payload shares the plot row's shape but not its meaning); `get_cached_plot(max_age_s=)` bounds a row's *age*, which for the gap profile (`core.query.GAP_PROFILE_TTL_S`, 15 min) is a growth bound on back-scrolling, not a data invalidation — the entry dies with a `cache_epoch` bump anyway.
