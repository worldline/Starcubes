Under the hood

How a billion rows stays snappy.

[Source DB] [core/etl.py] [Postgres] Oracle ┌─ Extract ────┐ starcubes_meta Postgres ─────► │ Transform × N ├──► starcubes_<name> MySQL └─ Load (COPY) ──┘ ├ fact (RANGE) MSSQL └ dim_* (smallint) │ ▼ viz / chart.html + plot_json cache
Storage

Compact star schema

Dim FKs are smallint — 2 bytes per row, not 20.

Layout

Partitioned + unlogged

RANGE on time, BRIN index. Drop a partition to forget data.

Throughput

3-stage pipeline

Extract → N×Transform → COPY FROM. Multiprocess.

Latency

Two caches

Server: frozen count(*) by hash. Client: natural calendar blocks.

Append-only ETL never invalidates cache. Historical mutations bump an epoch.
