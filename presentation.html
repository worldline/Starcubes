01 Design decision

One Postgres. One schema per source.

starcubes_payments
fact · dim_app · dim_loc · …
its own shape, its own dimensions
starcubes_requests
fact · dim_status · dim_host · …
completely different shape — and that is fine

Two sources rarely have compatible shapes. Each lives in its own Postgres schema, so neither has to compromise.

02 Design decision

Two bytes per dimension. Not twenty.

The fact table carries smallint foreign keys into per-dimension tables — that is where the 93 bytes per row come from.

2 B — one dimension key 93 B — one fact row, all dimensions included

Day / week / month range partitions, gap-filled automatically · BRIN on the time column · indices built after the first bulk load, not before.

03 Design decision

Extract. Transform. Load.

stage 1
Extract
SELECT beyond the high watermark, windowed and resumable
→
stage 2
Transform
new dimension values keyed as they appear — one vectorized Series.where per chunk replaces every dim key in a single numpy pass; super-fast, and it scales across N worker processes
→
stage 3
Load
COPY FROM into the partitioned fact table

Incremental on the watermark, killable mid-run, with a late-arrival overlap for sources that publish out of order.

04 Design decision

Dimensions come in three flavours.

imported
From a lookup table
A source table the ETL joins against and copies on each load.
inline
From a CSV in the config
Small enumerations live in the datasource definition itself.
auto
Discovered during load
New values are found and keyed as the rows arrive — nothing to pre-register.
05 Design decision

Configure a source in a form, not in dbt.

Base table, watermark column, a row per fact column — that is the whole model.

base table watermark column one row per fact column

Save it as a profile — a YAML file, deliberately without any credentials — and the next install is one click.

1 / 4 Using it

Add a datasource from the browser.

localhost:8080/sources/
localhost:8080/profiles/

New Datasource — name, dialect, connection URL. Apply a profile, or fill in base table, watermark and fact columns yourself.

2 / 4 Using it

Run the load. Watch it work.

…/manage#etl
…/manage#storage

Incremental, a manual window override, forever at an interval — or kill it. Every run writes a row and its own log file. Storage cost per table and per partition, right next to it.

3 / 4 Using it

Slice it without writing SQL.

localhost:8080/?name=…&group_by=…
?filter=…

Group by any dimension, filter on any other — nested AND/OR, is-in / contains / starts-with. Filters live in the URL: a view you found is a link you can send.

4 / 4 Using it

Click a bar. See what is in it.

drilldown
alarms · console

Every bar breaks down to its dimensions and then to individual primary keys. The bell carries the chart's filter into a new alarm; breaches are recorded as episodes with a first-breach and a closed watermark. And a read-only SQL console with history and CSV export is one click away.
